Agent optimizer: better instructions, measured

Prompt engineering is a slow, subjective loop: write, test, find weaknesses, rewrite. The agent optimizer automates it with an evaluation-driven cycle that improves instructions, tool descriptions, skills and model choice against your own dataset.

You then promote the winning candidate to a new prompt-agent version, or apply it to your hosted agent's configuration and redeploy.

TargetWhat changesPrompt agentHosted agent
Instruction tuningRewrites and refines the system prompt.YesWhen an instructions.md exists

  1. Open the agent's Optimize tabBuild › Agents › your agent › Optimize. No code changes are required for prompt agents.
  2. Select the baseline versionThe prompt-agent version you will compare candidates against.
  3. Choose a datasetGenerate one from agent traces, pick an existing Foundry dataset, or upload one.
  4. Choose evaluation criteriaBuilt-in or custom evaluators for the behaviors you want to improve.
  5. Choose models and review the cost estimatePick the evaluation model and candidate models. The Review step shows a modeled Minimum, Estimated and Maximum cost before you submit.
  6. Review results and promoteCompare scores, the before-and-after prompt and per-evaluator results, then promote the best candidate to a new version.

Hosted agents must be optimizer-ready: the agent loads its configuration (instructions and optionally skills and tool definitions) through the optimization package, so it can load a candidate during a run with no feature flags. Foundry Toolkit for VS Code scaffolds this automatically; with the Azure Developer CLI you add it yourself. Datasets can be local JSONL files or datasets registered in your project, including those generated from traces. After a run, apply the winning candidate locally, review, and redeploy.

azd ai agent optimize apply --candidate <candidate-id>
azd deploy
Your tools really run. The optimizer invokes your agent against every task in the dataset. If the agent calls APIs, databases or third-party services, those calls execute on each evaluation run. Use test endpoints or mock the tools during optimization.
  • Two models are used: an eval model that scores responses (any chat-completion model) and an optimization model that generates candidates (a more capable one usually produces better candidates).
  • The portal estimate is modeled from static token assumptions. It is neither a spending limit nor a substitute for your invoice. Measured token usage appears after the run.
  • The pre-run estimate is currently available for prompt agents in the portal; hosted-agent flows show post-run token usage.
