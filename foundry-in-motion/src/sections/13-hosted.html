Hosted agents: architecture, compute and runtime

Hosted agents are containerized agent applications that run on Foundry Agent Service. Your code (any framework) handles orchestration and calls models from the catalog; the platform owns the endpoint, identity, scaling, session state and observability around it.

Architecture

Adapted from the architecture in the hosted agents documentation. Each session gets its own isolated sandbox; scaling happens per session, not per replica.

  • Per session, not per replica. A new VM-isolated sandbox is created for each session on demand. There is no replica count to configure and no warm pool to size. The CPU and memory you set describe a single session.
  • Right-size with data. Run a representative workload and watch CPU, memory and request duration in Application Insights (Investigate › Performance). If sustained peaks exceed about 70% of allocation, raise the next version; if they stay well below, lower it to cut cost. Versions are immutable, so retest after each change.
  • Disk. Up to 20 GiB per session at 1 vCPU or larger (scaled down for smaller tiers); about 20% is reserved for the system. The rest is shared by your image, $HOME and other writable paths.

Compute follows the session, not the request. Click a state, or let it play.

Active

Compute is running and requests are routed to it. $HOME and /files are available. Every request resets the idle timer.

Idle

No requests for the idle timeout (2 to 240 minutes, default 15). The platform deprovisions compute and persists session state.

Resumed

The same session ID arrives again. New compute is provisioned and $HOME and /files are restored, so files written earlier are still there.

  • The platform permanently deletes a session after 30 days of inactivity.
  • Responses protocol: the conversation ID is primary and the platform keeps history. Invocations: the session ID is primary and you manage state (for example in Cosmos DB or the durable state store).
  • A durable state store Preview holds keyed JSON items that survive crashes, restarts and idle eviction (default 30-day idle window), handy for framework checkpoints.

IdentityScopePurpose
Agent identity (Entra ID)Per agent, created at deployWhat the container authenticates with at run time: models, tools, downstream Azure services.
Project managed identityProject-wide, system-assignedPlatform infrastructure work, for example reading your container registry. Not the agent's runtime identity.
  • The agent identity can reach model inference and session storage by default. For other resources (such as your own storage), assign RBAC roles to the agent's Entra identity.
  • User-invoked calls can use OAuth 2.0 on-behalf-of with the user's delegated permissions. Autonomous calls use the agent's own identity.
  • No secrets in images or environment variables. Use managed identities, connections and Key Vault.
  • Private networking: deploy within network-isolated Foundry resources and send outbound traffic through your virtual network. Projects created after June 25, 2026 support a private Azure Container Registry.
  • Network egress controls Preview in a guardrail limit which outbound destinations a hosted agent may reach.
  1. Write the agentUse Microsoft Agent Framework, LangGraph or your own code, with a protocol library that serves HTTP or WebSocket, health checks and OpenTelemetry.
  2. Package and pushBuild a container image and push it to Azure Container Registry.
  3. Create a versionWith the Azure Developer CLI (azure.ai.agent service in azure.yaml) or the Foundry SDK: image, CPU and memory, environment variables and protocols. Each call creates an immutable version.
  4. Call the endpointLive as soon as it deploys; publishing is only for Teams and Microsoft 365.
  5. ObserveAn Application Insights connection string is injected automatically. Traces appear under Investigate › Transaction search.
  6. IterateShip a new version to change code, size, variables or protocols. An endpoint serves one version at a time with 100% of traffic; traffic splitting is not supported.

Hosted agents have full access to Foundry-managed tools through a Toolbox MCP endpoint (Code Interpreter, web search, Azure AI Search, OpenAPI, MCP, A2A, skills). With Microsoft Agent Framework use FoundryToolbox (Python) or AddFoundryToolboxes (.NET).

  • Pricing: managed hosting runtime is billed on consumption of CPU and memory during active sessions. See the Foundry pricing page for current rates. You also pay for the models and tools the agent calls.
  • Regions (31 at the doc date): Australia East, Brazil South, Canada Central and East, Central US, East US and East US 2, France Central, Germany West Central, Italy North, Japan East and West, Korea Central, North Central US, Norway East, Poland Central, South Africa North, South Central US, South India, Southeast Asia, Spain Central, Sweden Central, Switzerland North and West, UAE North, UK South and West, West Central US, West Europe, West US and West US 3.
  • Languages: Python and C#.
  • Third-party risk: third-party servers, code and non-Azure-direct models are used at your own risk and you own responsible AI mitigations.
